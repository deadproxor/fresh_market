## 1. Как устроен проект

Это PWA на чистом JavaScript без сборщика: лендинг, витрина для покупателей и отдельная админка для закупщика. Данные лежат в Supabase, фото в Cloudinary, распознавание товаров делает Gemini Vision. Заказы работают по модели «консьерж»: покупатель оформляет заявку без цены, закупщик вводит сумму чека после рынка.

## 2. Что исправлено

- **Заказ одной серверной функцией.** Витрина вызывает `create_order`, и функция есть в живой базе (запрос к `pg_proc`). По тексту SQL сервер сам задаёт статус и оплату, стоимость доставки по зоне и номер из последовательности, а заказ и позиции пишет в одной транзакции. Какая именно версия функции развёрнута, не проверено.
- **Роли администратора.** Email убран из клиентского кода, `isAdminUser` смотрит только на роль в `app_metadata`. В SQL политики переписаны на `is_admin()`, функция в базе есть. Политики после коммита не выгружались, а `protect_profile_role` в базе не найдена (см. 3.1).
- **Секреты и URL.** Экспорт настроек не содержит Cloudinary API Secret, URL Supabase проверяется при сохранении и при импорте (`*.supabase.co` или localhost).
- **Ссылки.** `sanitizeUrl` применяется ко всем `img_url`, к ссылке на чек и к аватару, `<img src>` без проверки не осталось.
- **Хранилище админки.** Если URL и ключ Supabase не заданы в настройках, админка берёт вшитые значения, а не переходит на локальное хранилище.
- **RLS в живой базе.** Старые публичные политики на `products`, `orders`, `order_items` и `profiles` удалены, в выгрузке от 17 октября 11 нужных политик.
- **Колонки заказа.** В живой базе есть все поля, которые отправляет витрина (по выгрузке от 17 октября). Типы и ограничения не проверены.
- **XSS в админке.** `loadAdminOrders` экранирует все поля заказа, `utils.js` подключён в админке, у страницы есть `noindex`.
- **Заказы не теряются молча.** При ошибке показывается предупреждение, заказ получает статус `pending_sync` и досылается при открытии списка заказов. Статусы и поля витрины совпадают с админкой, зона доставки уходит в заказ.
- **Репозиторий.** `*.md` больше не игнорируются, документация и схема лежат в git. Оригиналы PNG убраны из индекса, папка онбординга весит 5,2 МБ вместо 11.
- **Service worker'ы** не перехватывают чужие запросы и кэшируют файлы по одному, так что сбой одного файла не ломает установку.
- **Локали** выровнены (по 361 ключу), админка использует общие `utils.js` и `categories.js`.

## 3. Критичные проблемы

### 3.1. Развёртывание SQL в базе подтверждено частично

По запросу к `pg_proc` в живой базе есть `create_order` и `is_admin`, а `protect_profile_role` отсутствует. Значит, триггер защиты роли не создан: политика `UPDATE` на `profiles` позволяет пользователю менять свою колонку `role`. Код сейчас не использует эту колонку для прав, но опираться на неё нельзя.

Политики после последних коммитов не выгружались. Неизвестно, вызывают ли они `is_admin()` и остались ли политики `INSERT` на `orders` и `order_items`. Версия развёрнутой `create_order` тоже неизвестна: если её нет или она устарела, витрина молча переходит на прямую вставку и пишет предупреждение только в консоль.

**Решение:** выгрузить политики, триггеры профиля и тексты функций, затем выполнить блок с `protect_profile_role` из `SUPABASE_SETUP.md` и сделать пробный заказ под обычным покупателем.

```sql
select tablename, policyname, cmd, roles, qual, with_check
from pg_policies where schemaname = 'public' order by 1, 2;

select tgname from pg_trigger
where tgrelid = 'public.profiles'::regclass and not tgisinternal;

select pg_get_functiondef('public.is_admin'::regproc),
       pg_get_functiondef('public.create_order'::regproc);
```

### 3.2. Заказ можно создать в обход `create_order`

Политики `Users can create orders` (на `orders`) и `Users can insert order items` остаются в SQL и в базе. Покупатель может вставить заказ напрямую через REST с любым `status`, `payment_status` и `grand_total`. Серверная функция этого не предотвращает, пока прямая вставка разрешена. Переход витрины на прямую вставку при отсутствии функции держит эти политики живыми.

**Решение:** после проверки из 3.1 удалить обе политики `INSERT` (функция объявлена как `SECURITY DEFINER` и в них не нуждается) и убрать переход на прямую вставку из `shop.js`.

### 3.3. Пробелы в самой функции `create_order`

- **Чужой заказ можно перезаписать.** `ON CONFLICT (id) DO UPDATE` не проверяет владельца: зная чужой `p_order_id`, можно изменить телефон, адрес и комментарий и добавить позиции в чужой заказ. UUID трудно угадать, но проверка нужна: `WHERE orders.user_id = auth.uid()`.
- **Зону доставки выбирает клиент.** Функция верит `p_delivery_zone`, а для неизвестного значения берёт 3,50. Покупатель может указать `zone_1` и платить 1 доллар вместо 3,50.
- **Нет проверки входных данных.** Не ограничены количество (отрицательное, огромное), число позиций, длина имени, адреса и комментария. Название, категория, фото и `estimated_price` берутся из запроса, а не из `products` по `product_id`.
- **Номера.** Каждая повторная отправка тратит номер из `order_number_seq`, номера не сбрасываются по дням, хотя формат `FM-ГГММДД-NNN` это подразумевает, а дата берётся по времени сервера (UTC), не Камбоджи.
- **Права.** После `GRANT EXECUTE ... TO authenticated` нужно добавить `REVOKE ... FROM PUBLIC, anon`. Сейчас анонимный вызов отклоняет только проверка `auth.uid()`.

**Решение:** передавать в функцию координаты или проверять зону из допустимого списка, брать данные товара из `products`, добавить лимиты и проверку владельца.

### 3.4. Секреты и токен администратора

- Cloudinary API Secret и ключ Gemini по-прежнему хранятся в `localStorage` открытым текстом, подпись удаления фото считается в браузере.
- Лендинг, витрина и админка работают на одном origin, если выкладываются на один домен. XSS в любой из них читает `localStorage` админки.
- Данные заказа из `create_order` (имя, фото, название позиции) приходят от клиента, поэтому на экране позиций, когда он появится, их нужно экранировать так же, как в `loadAdminOrders`.

**Решение:** вынести операции с секретами (удаление в Cloudinary, при необходимости вызовы Gemini) в Supabase Edge Function и вынести админку на отдельный поддомен.

## 4. Важные проблемы

- **Скрипт в `SUPABASE_SETUP.md` не удаляет старые политики.** Он пересоздаёт только политики с известными именами. Старые `Allow ...` были причиной открытого RLS, и на другой или восстановленной базе они останутся. Нужны явные `DROP POLICY IF EXISTS` для них.
- **Геоданные клиентов уходят третьим сторонам.** Для расчёта маршрута и адреса координаты отправляются на `router.project-osrm.org` и `nominatim.openstreetmap.org`. Об этом стоит сказать в политике приватности. Запасной расчёт по прямой есть.
- **Репозиторий публичный.** В документации и в прошлых версиях аудита указан адрес `deadproxor@gmail.com` и описаны ранее найденные уязвимости. Это приемлемо только если всё закрыто в живой базе (см. 3.1).
- **Удаление товара широкое.** Запрос `DELETE ... name_en=eq.` убирает все записи с таким названием, а его ошибка проглатывается. Фото в Cloudinary удаляется, даже если на него ссылается другая запись.
- **Нет базовой защиты страниц.** Нет CSP, `supabase-js@2` подключается без закреплённой версии и SRI (у Leaflet SRI есть).
- **Мелочи.** `dev-server.py` по-прежнему слушает `0.0.0.0` и открывает файлы всей сети. Список моделей Gemini вшит в код, его стоит сверить с актуальным у Google.

## 5. Качество, вес и поддержка

Хорошо сделано: сессия администратора в `sessionStorage`, ключ Gemini в заголовке `x-goog-api-key`, SRI у Leaflet, экранирование данных и проверка ссылок во всех местах, очередь повторной отправки заказов. В SQL заказ создаётся атомарно, номер выдаёт последовательность, права сведены к `is_admin()`, а роль в профиле должна защищаться триггером (в базе он пока не создан). Адрес Supabase проверяется при сохранении и импорте настроек. Локализация полная, общий код вынесен в `js/shared/`.

- **Дублирование сократилось, но не исчезло.** Вшитые URL и ключ Supabase теперь объявлены в `utils.js`, но их запасные копии остались в `shop.js`, `admin-catalog.js` и `admin-auth.js`. В `shop.js` и админке есть ещё копии `sanitizeUrl`.
- **Монолиты растут.** `admin-catalog.js` 3873 строки, `shop.js` 3196, `components.css` 3608.
- **Локализация неполная в коде.** В `shop.js` остаются русские запасные тексты рядом с i18n, админка целиком на русском.
- **Версии поднимаются вручную и не совпадают.** `APP_VERSION` 1.4.9, кэш админки v1.5.17, кэш магазина v1.5.33, параметры `?v=` от 1.4.10 до 1.4.36.
- **Нет тестов, линтера и CI.** SQL лежит в Markdown, а не в `supabase/migrations`, и не применяется автоматически. Поэтому состояние базы и файла уже расходилось, как с политиками и колонками.
